## V1 —— 初版打通预约主流程（2026-09-08，`28fb0fe`）

**目标**：先把东西"做出来并看得见"——把房间 / 座位预约从登录到落库的核心链路跑通，本地可预览。

**做了什么**
- **两种资源模型**：8 个房间（801–808）；其中 803 公共自习室按座位预约。
- **预约规则**（写在 `src/config/index.js` + `src/utils/booking.js`，为纯函数、可单元测试）：
  - 半小时粒度（`SLOT_MINUTES = 30`），全天可约，可约未来 7 天（`BOOKING_WINDOW_DAYS = 7`）。
  - 普通房间：单次 ≤3 小时直接预约；>3 小时转为**申请**（需填原因，最长 24 小时；超 4 小时未处理由定时云函数自动通过）。
  - 803 座位：无申请流程，直接预约，单次最长 10 小时；支持"单座 / 座区"两种选择方式。
  - 同一用户禁止时间重叠（跨房间 / 座位）；公开页只显示占用状态，不显示预约人身份。
- **并发防重复占用**：用 `slots` 集合自定义 `_id`（房间 + 时间片）的唯一性做锁，避免两人抢到同一时段。
- **登录与权限**：`login` 云函数返回 openid 与是否管理员；管理员白名单存于 `admins` 集合。
- **管理后台**：房间资料编辑（图片 / 介绍）、预约管理、申请审核。
- **中英双语**固定文案 + 每个页面底部统一"联系我们"。

**结果**：`npm run build:mp-weixin` 产出 `dist/build/mp-weixin`，导入微信开发者工具即可预览。

## V2 —— 预约后返回与状态刷新（2026-10-09，`979ce54`）

**观察到的问题**（来自实际操作，逐条描述）

1. 提交预约成功后固定跳转到"我的"页，用户想继续约同一房间得重新一层层点回去，**路径断裂**。
2. 从预约页返回房间 / 座位页时，占用状态仍是进入时的旧数据（页面 `onShow` 未刷新），**可能看到已经被别人占用的时段**。

**本轮改动**（只处理"预约完成后的页面流转与数据新鲜度"这一类问题）

- `src/pages/booking/booking.vue`：提交成功后由"跳转我的页"改为**返回上一层房间 / 座位页**；页面栈为空时回退到对应资源页。
- `src/pages/room/room.vue`、`src/pages/seat/seat.vue`：新增 `onShow` 时刷新一次占用数据。
- 同上两文件：把云数据库读取包进 `try/catch`，云环境未就绪时不再阻断页面渲染。

**怎么验证的**

- 纯函数规则测试：`npm run test` → **通过 18 项，失败 0 项**。
- 小程序构建：`npm run build:mp-weixin` → **Build complete**（产物 `dist/build/mp-weixin`）。
- 微信开发者工具手动复测：预约 → 返回 → 占用状态已更新。

## V3 —— 隐私修复：拆分公开占用表与私有联系方式表（2026-10-09，`863d486`）

**观察到的问题**

- `bookings` 集合为了支持前端展示 / 实时监听占用状态，权限被设为"所有用户可读"。
- 但同一个集合里又存了预约人的**姓名、手机号**和申请原因。公开页面上"不显示身份"只是前端没有渲染，**数据本身任何用户都能读到**。
- 这与课程要求（不泄露隐私数据、不收集不必要的敏感信息）冲突。

**本轮改动**（只处理"个人信息暴露"这一类问题）

- **拆成两张表，用同一个 `_id` 关联**：
  - `bookings`（所有用户可读）：只保留 `roomId / seatIds / startTs / endTs / type / status` 等**占用信息**，不再有姓名、手机号、申请原因，也不再写 `_openid`。
  - `booking_details`（默认权限，仅云函数可读）：保存 `name / phone / reason / _openid`。
- `booking` 云函数：预约时先写 `bookings`，再写 `booking_details` 与 `slots`；任一步失败会把三处一起回滚。取消 / 撤销 / 报到 / 详情查询改为通过 `booking_details` 校验归属，并兼容拆分前的旧数据。
- `admin` 云函数：`listAllBookings` / `listApplications` 会关联 `booking_details` 再返回，**管理端页面不需要任何改动**，姓名、手机号、申请原因照常显示。
- 新增 `migrateBookingDetails` 动作：把旧记录里内联的联系方式搬到私有表，并从公开表清除。

**怎么验证的**

- 纯函数规则测试：`npm test` → **通过 18 项，失败 0 项**。
- 小程序构建：`npm run build:mp-weixin` → **Build complete**（新逻辑已同步进产物 `cloudfunctions`）。
- 云函数语法检查：`node --check` 通过（`booking`、`admin`、`autoApprove` 三个云函数）。
- **待补**：部署新版云函数后，在微信开发者工具里真机跑一遍"预约 → 管理端查看联系方式 → 取消"的完整链路。

**为什么管理端仍然能看到联系方式**

管理端列表的数据来自 `admin` 云函数：它先查 `bookings`，再按 `_id` 批量读取 `booking_details` 合并后返回。云函数拥有完全权限，所以公开表里没有联系方式，也不影响管理端展示。
